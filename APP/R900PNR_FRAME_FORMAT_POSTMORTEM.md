# R900PNR 视频流转发周期性"停摆" —— 故障报告

| 项 | 内容 |
|---|---|
| 日期 | 2026-09-17 |
| 严重度 | 高 —— 视频链路周期性完全中断，交付率低至 64% |
| 影响范围 | 所有走 R900PNR 发送自定义载荷的代码。**从本工程第一天起就存在** |
| 修复 | `hgic_raw_send_ether()` → `hgic_raw_send()`（发送端 1 行；接收端剥头 1 处） |
| 涉及文件 | `APP/User_App/src/App_R900PNR_Handle.c`（唯一逻辑改动） |
| 验证 | 200 Kbps 连续 **18 分 47 秒**；4000 Kbps **41 秒**（该速率修复前 1.7 秒即死）。均为 `lostT=0 stall=0 bad=0`、`vidT = seq + 1` |

---

## 1. 结论先行

**根因：我们一直把"裸载荷"喂给了契约要求"以太帧"的函数。**

厂商 API 里有两个发送函数，注释写得很清楚：

```c
/* send raw data: needn't care the packet format.
    data: raw data     len : raw data len                */
int hgic_raw_send(unsigned char *dest, unsigned char *data, unsigned int len)

/* send ethernet frame
    data: ethernet frame packet     len : frame len       */
int hgic_raw_send_ether(unsigned char *data, unsigned int len)
```

`hgic_raw_send_ether()` 的 `data` **必须已经是一个完整的以太帧**（`dst[6] + src[6] + type[2] + 载荷`），它把这个 buffer 原样拷到模块自己的帧头之后，不做任何加工。

而我们传进去的是 1400 字节的视频帧：

```
offset 0   magic   uint16   0x4E56
offset 2   seq     uint32
offset 6   flags   uint8
offset 7   reserved uint8
offset 8   crc32   uint32
offset 12  payload 1388 字节
```

**从模块的视角看，字节 `[0..5]` 就是目的 MAC，字节 `[12..13]` 就是 ethertype。** 于是每一帧的"目的地址"实际上是：

```
56 4E <seq 的 4 个字节，小端>
```

**一个随着帧序号逐帧变化、且从不属于任何设备的 MAC 地址。**

`hgic_raw_send()` 才是给裸载荷用的：它自己构造以太头（`dst` = 指定/`hgic.bssid`，`src` = 本模块 MAC，`type` = `HGIC_RAW_ETHTYPE 0x66AA`），接收端拿到的就是"以太头 + 我们的载荷"。

**与上位机应用逻辑、射频、SD 卡、关联状态全部无关。** 一行 API 用错。

---

## 2. 现象

200 Kbps 视频流（1400 字节/帧，18 帧/秒），两块板相距几厘米（`rssi` 在 −10 ~ +3 dBm 之间）。

**正常时完美，但每隔一段时间会"停摆"：**

```
[RX STAT] pkts=20 vid=18 oth=2 lost=0 bad=0 ... seq=616   ← 正常
[RX STAT] pkts=0  vid=0  oth=0 lost=0 bad=0 ... seq=616   ← 停摆开始
[RX STAT] pkts=0  vid=0  oth=0 lost=0 bad=0 ... seq=616      ...持续 7 秒 ~ 100 秒以上
[RX STAT] pkts=19 vid=17 oth=2 lost=0 bad=0 ... seq=633   ← 自己恢复
[RX STAT] pkts=20 vid=18 oth=2 lost=413 ... seq=1064      ← 丢掉一大批
```

停摆的特征，每一条都反复实测确认：

| 观察 | 说明 |
|---|---|
| **完全单向** | STA→AP 一个字节都过不来；AP→STA 的探测帧 25 秒里一帧不丢 |
| **彻底** | 连 STA 模块**自己**发的 300 字节广播（`oth`）也一起消失 |
| **两端都声称健康** | `conn=1`、`aid:1` 全程不变，模块**不上报任何异常事件** |
| **恢复要重新关联** | 每次恢复都伴随 `STA:xx disconnected` / `connected`，3/3 次 |
| **时长不定** | 1.7 秒 / 7 秒 / 25 秒 / 32 秒 / 35 秒 / 50 秒 / 100 秒以上 / 11.6 分钟，没有固定周期 |
| **强烈依赖速率** | 4000 Kbps 时 **1.7 秒**就死；200 Kbps 能撑几十分钟 |
| **稳态 CRC 错误 ~3.7%** | `bad` 计数器，与速率无关，降速也不消失 |

**交付率**在 64% ~ 100% 之间剧烈波动，取决于停摆什么时候来。

---

## 3. 为什么现象长这样

**这一节要分清"已证明"和"推断"。** 模块固件是黑盒，我们只能从行为反推。

### 已证明的

1. **帧确实到达了，只是被当成畸形帧处理。** 停摆之外的时间，`vid=18`、magic 正确、`len=1400` 全部正常 —— 说明模块**不校验**这个 buffer，只是原样转发字节。所以基本传输是通的，问题只在特定条件下爆发。
2. **模块在处理过程中动了我们的数据。** 稳态 `bad` 稳定在 ~3.7%（CRC 覆盖的是载荷 `[12..1399]`，不看帧头）。换了正确的 API 之后 **`bad` 直接变成 0** —— 这是独立于停摆的第二个证据：模块之前确实在碰它不该碰的字节。
3. **AP 端的模块在停摆期间"什么都没收到"。** 不是"收到了不上交"：它连 INT 都不拉（`int=0~4`，那几个全是命令回包），而且 STA 模块自己的广播也一起没了。模块自己也知道自己链路有问题 —— 发送端 `tbr`（模块自报的 TX 速率）会在停摆开始后以 5 秒一档往下走，最终归零。

### 推断的机制（最符合观测，但未证实）

以太帧的目的 MAC 在 802.11 里决定了**聚合（A-MPDU）和块确认（Block-ACK）会话**的归属。目的地址**每一帧都在变**，意味着：

- 发送侧每帧都在试图建立到"不存在的站"的新会话
- 接收侧对应地不断产生无法正常关闭的接收状态，**接收缓冲被这些悬挂会话占死**
- 缓冲满 → 什么都交不上去（连模块自己的广播也进不来）→ AP 端 `int/rd` 归零
- 只有**重新关联**能重建全部链路状态 → 所以恢复永远是 `disconnected`/`connected`

**这个推断解释了全部六条现象**：单向（只有一个方向有批量流量）、彻底（缓冲满，不分来源）、两端都健康（MAC 层不报错）、恢复靠重关联（重建状态）、时长不定（取决于什么时候占满）、强烈依赖速率（灌得越快越早满）。

**但它没有被证实。** 反过来说，**它也不需要被证实** —— 契约错误是客观存在的，修好它就够了，实测也已经证实修好了。

### 为什么"3.7% 的 CRC 错误"这么关键

`bad` 是**唯一一个从不开停摆、只反映稳态损坏**的计数器。之前无论怎么降速、改预算上限、换信道、加探针，它都纹丝不动地停在 3.7%。**停摆被修好的同时它归零**，说明这两件事是同一个根因的两个表现。

## 4. 排查过程

一共十几轮上板实验。这里记的是**有效的推理链**和**踩过的坑**。

### 4.1 先被排除的（每条都有实测依据）

| 假设 | 怎么排除的 |
|---|---|
| 干扰 / 阻塞台 | 干扰会把两个方向一起打掉。实测 AP→STA 探测帧在 25 秒停摆里**一帧不丢** |
| 信道跳变 | 同上；且 `center freq` 探针在停摆期间采样 11 次全是同一个值 |
| 距离 / 接收去敏 | 板子拉开后仍停摆 |
| 模块过热 | `temperature` 全程 32–35 °C 平直 |
| 应用层发送逻辑 | STA 模块**自己**的广播也一起丢，那些不是我们的代码发的 |
| 关联断开 | 两端 `conn=1` / `aid:1` 全程不变 |
| 站点链路状态 / AP 射频 | **主动干预**：停摆时 `disassoc_sta` 和 AP 射频重启都试过，都无效 |

### 4.2 关键的两步

**第一步：方向探测。** 加了一个 AP 侧每秒 2 次的空中广播（magic `0x5250`），STA 侧统计收到的帧数。

结果**决定性**：停摆 25 秒里，STA **每秒都收到 2 个探测帧**，而 AP 一个字节都收不到。**故障是单向的** —— 这一条一次性清空了上面"干扰/信道/去敏"整族假设。

**第二步：注意到"什么帧能过"。** 有一次恢复之后出现过 13 秒的奇特状态：

```
pkts=2 vid=0 oth=2      ← AP 收得到 STA 模块的 300 字节广播，收不到我们的 1400 字节视频帧
```

**这是整个排查里第一次把"无线电"和"我们的帧"分开。** AP 的接收机没坏，STA 的发射机没坏 —— **只有我们的帧过不去。**

顺着这条线往下一看：**链路上所有能过的帧，无一例外都是格式正确的以太帧**（模块自己的广播、AP 的探测帧）；**所有过不去的帧，都是我们的**。

### 4.3 踩过的坑（写下来避免重复）

- **`CMD:128, RESP:Fail[-524]` 是假失败。** `start_assoc` 返回 −524，但模块其实已经关联上了（`get_connect_state` 返回 `OK[9]`）。**别再把 −524 读成"没关联"。** 同一个码也用来表示"命令不存在"。
- **`bgrssi`（CMD 146）的返回值不可解码。** 厂商按 max/min/avg 三个有符号字节解析，但拿到的是 `max:1 min:2 avg:-126` 这种物理上不可能的值。**不要再引用它。**
- **`tbr` 的绝对值不可信。** 它只在模块每 5 秒推 `HGIC_EVENT_TX_BITRATE` 时变化，两次实验里甚至方向相反。看它的**趋势和时机**，不要引用具体数值。
- **`get_sta_list`（CMD 53）能应答 ≠ 空中是通的。** 它问的是接收端**自己**模块的内部站表，走的是 MCU↔SDIO，**完全不碰射频**。排查早期把这条当成了"链路活着"的证据，是错的。
- **厂商的 `STA:xx connected` 事件是会来的** —— 只在**重新关联那一刻**出现。之前几轮因为没见到就断言"事件从不触发"，是错的。
- **`git log -S` 说历史代码用的是 `send_ether`，把人往错方向带了。** 修复者凭的是 **API 契约**，不是历史。**契约比历史可靠。**

## 5. 修复

### 发送端（STA）

```c
/* 改前 */
ret = hgic_raw_send_ether(Vid_Tx_Frame, VID_FRAME_LEN);

/* 改后 */
ret = hgic_raw_send(Peer_Mac, Vid_Tx_Frame, VID_FRAME_LEN);
```

`Peer_Mac` 是对端模块的地址，**从 AP 探测帧的源地址字段学来**（探测帧是格式正确的以太帧，`src` 就是 AP 的 MAC）。学到之前用广播兜底。

这也顺手给了一个一直未使用的静态变量真正的用途。

### 接收端（AP）

`hgic_raw_send()` 会在载荷前面加上 14 字节以太头，所以接收端要先剥掉再解析：

```c
if (len <= sizeof(struct hgic_eth_hdr)) { Rx_Other_Pkts++; return; }
vid_data = &data[sizeof(struct hgic_eth_hdr)];
vid_len  = len - (uint32_t)sizeof(struct hgic_eth_hdr);
/* 之后用 vid_data / vid_len 判断是不是视频帧 */
```

`oth`（模块自己的流量）仍然把以太头留着给 `App_RxNoticeOther` 打印 —— 那段日志的价值就在于那个头。

## 6. 为什么这样就能解决

`hgic_raw_send()` 构造出来的帧：

```
dst[6] = 对端模块 MAC（固定、有效）
src[6] = 本模块 MAC
type[2] = 0x66AA
payload = 我们原本的 1400 字节（magic + seq + flags + crc + 载荷）
```

**这和模块自己发出的帧在形式上完全一致** —— 固定的、真实存在的目的地址，正确的 ethertype。

于是：

1. 目的 MAC 不再随序号变化，聚合/块确认会话能正常建立和关闭
2. 接收侧不再产生悬挂的接收状态，缓冲不会被占死
3. 模块不再需要把它不理解的内容当作帧头去处理 —— 这也是 `bad` 从 3.7% 归零的原因

**换个角度说：修复之后，链路上不再有"畸形的帧"。** 之前唯一的异常输入消失了。

## 7. 验证数据

**两次实验，第二次是关键。**

### 修复后第一次（200 Kbps，同板同配置）

```
14:07:06.081   [RX] first video frame seq=0 len=1400
14:08:52.363   seq=1895  vidT=1896  lostT=0  stall=0
```

106 秒 `stall=0`。但 Run 6 曾经干净跑过 11.6 分钟才第一次停摆，**所以这时候还不能下结论**。

### 修复后第二次（跑满 18 分 47 秒）

```
14:25:52.930   seq=20094  vidT=20095  lostT=0  stall=0  bad=0
```

- **`vidT = seq + 1`** —— 从第 0 帧到第 20094 帧，**一帧没丢**
- **`stall=0`** —— 1127 个统计窗口里没有一个空窗
- **`bad=0`** —— 稳态 CRC 错误从 3.7% 归零
- **`tbr` 全程 13738 ~ 14066**，没有像以前那样一路走低
- `rssi:3` —— 板子仍然贴在一起，**跟射频无关**

**对照：修复前每一轮都在 ~35 秒内停摆**（除 Run 6 的 11.6 分钟）。**18.8 分钟是原记录的 1.6 倍。**

### 修复后第三次（2026-09-18，回到目标速率 4000 Kbps）

上面那两次都跑在 200 Kbps，而这个故障强烈依赖速率。所以 `VID_TARGET_KBPS` 改回 4000 又跑了一轮：

```
09:18:14.895  rate=4009 Kbps seq=2213  vidT=2214 lostT=0 stall=0 bad=0
09:18:53.922  rate=4009 Kbps seq=16118 vidT=16119 lostT=0 stall=0 bad=0
09:18:55.927  rate=3976 Kbps seq=16831 vidT=16832 lostT=0 stall=0 bad=0
```

**41 秒、14618 帧、一帧不丢，`rate` 平在 4000，`bad` 同样是 0。**

**这是最有说服力的一条对照：修复前这个速率是 1.7 秒就死。** 同一工况下 41 秒 / 1.7 秒 = 24 倍。

之后 `rssi` 从 −3 一步掉到 −26 并继续降到 −40（台面上的物理变化，不是固件行为），链路进入弱信号状态，开始出现真实丢包。**但 `stall` 在整个约 175 个统计窗口里始终是 0，`[STALL]` 一次都没打印** —— 弱链路造成的丢包和这个 bug 的形状完全不同（前者 `vid` 仍非零，后者是 `vid=0`）。

## 8. 教训

1. **用厂商 API 之前先读它的契约注释。** `send_ether` 和 `send` 名字像、签名像、返回值一样，**语义完全不同**。一句话的注释就能省掉十几轮硬件实验。
2. **契约比仓库历史可靠。** 历史里查不到 `hgic_raw_send` 的调用记录，差点把正确方向否掉。
3. **"两端都健康但数据不通"要往"格式/契约"上想，不要只往"射频"上想。**
4. **一个不随故障波动、只反映稳态损坏的计数器（`bad`）价值极高。** 它不参与停摆，所以停摆修好时它归零，就成了独立的第二个证据。
5. **观察走到尽头时，最有效的一步往往是回头读文档，而不是再加探针。** 这个故障前后加了七八个计数器、两轮探针改造、还写了一套分级恢复动作，全都没定位到问题；最后是重新读了一遍两个发送函数的契约注释，一句话就找到了根因。**那套分级恢复一次都没触发过**（触发条件是"连续 3 秒无视频"，而真正的故障里 AP 每一轮都是 `stall=0`），它的唯一产出是"证明这条路不通"——这个结论已经进本报告，代码本身已删除。
6. **`fail=0` 不代表数据发出去了**，只代表模块收下了这个 buffer。
7. **两个本该一致的计数器一旦对不上，至少有一个在骗你。** `vidT` 和 `seq` 在链路良好时严丝合缝，一进入弱信号就分道扬镳 —— 这个"什么时候开始不一致"本身就是信息。

## 9. 后续验证的状态

**修复已在 200 Kbps 和 4000 Kbps 两个速率下验证通过**（数据见第 7 节）。原先"只在 200 Kbps 下验证过"的缺口已经补上。

**仍未做的：**

- **一次干净的 10 分钟 4000 Kbps 长跑。** 41 秒对比 1.7 秒是 24 倍，证据已经很强，但既然要定案就应该一次钉死。
  **已关闭（2026-09-18）：** 用户确认现在可以长时间连续运行。本条按"板上长期运行正常"收口，没有另留一份长跑日志。
- **09:18:55 那个 23 dB 的 `rssi` 台阶是什么造成的？** 那一轮里 `rssi` 从 −3 一步掉到 −26，随后漂到 −40。这是物理事件，不是固件行为。
  **已关闭（2026-09-18）：** 用户答复当时板子被挪动过（或已无法确定）。后半段按一次普通的弱链路实验处理，不再另立故障。**注意这一轮的结论只取前半段那 41 秒**——修复的验证用的是 `rssi -1` 的良链路区间。

**一个与修复无关、但会影响后续判读的发现：`lostT` 会大幅高估丢包。**

```
09:18:55.927   seq=16831  vidT=16832  lostT=0
09:18:56.892   seq=17186  vidT=17187  lostT=17     ← 一帧没丢，却记了 17 次
```

同一秒的窗口算术也对得上：`vid=355`，而 `seq` 从 16831 涨到 17186，**正好 355**。收到的和推进的完全一致。

后面偏差最大到将近 16 倍（`seq=47864 vidT=47790` 差 75，而 `lostT=1190`）。乱序（迟到帧让基准回退）和重复投递（重传上交两次）都能造成这个现象，**具体是哪个尚未定论**。

**判断真实丢包请用 `seq + 1 - vidT`，不要引用 `lostT`。**
